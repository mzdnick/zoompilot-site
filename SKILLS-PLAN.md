# Skills Plan: zoompilot-site

Generated by project-skill-architect on 2026-09-04.

Skills root: `.agents/skills/` (cross-tool — works in ZCode, Claude, Codex, Cursor).
Switch to `.zcode/skills/` only to override a same-named skill or force ZCode-only.

The root above is movable: the skills work from either directory. `.zcode/skills/`
takes priority during discovery, so use it only for overrides; `.agents/skills/` is
the default and should be committed so every tool and contributor gets the skills.

## Proposed skills

### 1. torque-chart
**Purpose:** Edit the EPS steering-torque chart (section 01) without breaking its framing rules or letting the wiki copy drift.
**Triggers when:** the user mentions the torque chart, steering chart, EPS chart, chart lines or numbers (44%, 1148, 800, 620), or asks to change `TorqueChart.astro`, `src/data/chart-geometry.js`, or `scripts/gen-wiki-chart.mjs` — even vague asks like "the graph".
**Priority:** high
**Structure:** SKILL.md
**Content:**
- One geometry file (`chart-geometry.js`) feeds two renderers: the site component and the wiki SVG. They must never drift.
- Framing rules fixed by user decisions: available torque only, two lines, no STEER_MAX line, no per-band demand curve, shared stretch drawn as accent dashes over stock, minimal labels in the plot.
- Honesty rule: the ceiling points and the 800 cap are measured; the curves between them are schematic. Keep the figcaption sentence that says so.
- The numbers sync map: 1148 / 800 / 620 / ~29 mph / ~32 mph / 44% appear as prose in three places besides the data file.
- Units: m/s internal, mph on the x-axis, torque in counts (never Nm).
- After any geometry change: `node scripts/gen-wiki-chart.mjs`, then commit in both repos.
- CSS touchpoints: draw-in animation, shared-tail fade, reduced-motion, mobile sideways scroll; leftover `.tc-cliff`/`.tc-band` classes must not be resurrected.
- Verification screenshots go to `.playwright-mcp/` or `/tmp`, never the repo root.

### 2. wiki-sync
**Purpose:** Run the site ↔ wiki content sync correctly and know which repo owns which content.
**Triggers when:** the user says "sync the wiki", changes supported-cars content, the changelog, or chart geometry, asks where a supported-cars wording fix belongs, or asks about `src/data/supported-cars.json`.
**Priority:** high
**Structure:** SKILL.md
**Content:**
- The wiki is a sibling checkout (`../zoompilot-wiki`), not a remote or submodule. `npm run sync:wiki` fails without it.
- The three jobs and their directions: supported cars wiki → site; changelog page and steering chart SVG site → wiki.
- `supported-cars.json` is generated — never hand-edit; wording fixes go in the wiki's `supported-cars.md`.
- The wiki changelog's "Upstream release notes" tail is hand-written and preserved verbatim; everything above the marker is regenerated.
- After a sync, commit in BOTH repos — the wiki auto-deploys from its own GitHub Actions.
- The wiki's `custom.css` mirrors the site's `site.css` (one brand system).

### 3. new-paint
**Purpose:** Add or change a paint on the CX-5 paint wall with every required edit site covered.
**Triggers when:** the user mentions paints, paint colors, chips, the paint wall or paint line, wants a new Mazda color, or edits `src/data/paints.js`, `ZP_PAINTS` in `Base.astro`, or `--p*` tokens / `.c*` chip classes in `site.css`.
**Priority:** high
**Structure:** SKILL.md
**Content:**
- One paint lives in five places (site.css tokens, paints.js, chip class, `ZP_PAINTS` map, footer paintline gradient). Same codes, same order everywhere.
- Light paints need `dark: true` in both JS copies plus the `--ink` CSS rule — nothing checks the coupling.
- Changing the default paint also means the `:root` initial values, `defaultPaint`, and the hand-computed `theme-color` meta.
- The chip boot animation covers 8 chips; a 9th needs a new `nth-child` delay.
- Verify by clicking every chip and checking the footer line.

### 4. new-release
**Purpose:** Add a release entry to the changelog so every consumer stays consistent.
**Triggers when:** the user mentions a new release, a version bump, "openpilot/sunnypilot released", a release-watch PR to fill in, or edits `src/data/changelog.js`.
**Priority:** medium
**Structure:** SKILL.md
**Content:**
- `ver` must match `version.h` on the upstream `main` branch (what the device home screen shows), not the date.
- Entry shape: newest first; trusted inline HTML from a small vocabulary (`<b>`, `<code>`, `<a>`, known entities) because sync converts exactly that vocabulary to markdown.
- `npm run stamp` after the edit — what it rewrites, GITHUB_TOKEN, why CI treats it as non-blocking.
- Consumers that derive from the file: the changelog section, RSS feed, the wiki page via sync, and the release-watch signal (wrong `ver` makes the bot misfire).
- Finish with `npm run sync:wiki` and commits in both repos; pushing the site repo deploys automatically.

### 5. site-copy-rules
**Purpose:** Keep product claims and steering terminology consistent and honest across all components.
**Triggers when:** editing any site copy, spec claims, or steering terminology — and before changing any claim about torque (44%), 12 units per frame, seven speed bands, 0 mph steering, supported years, or the alpha-longitudinal radar caveat.
**Priority:** medium
**Structure:** SKILL.md
**Content:**
- The steering part is the steering MOTOR — never "rack". Two vectors can silently reintroduce old wording: the generated `supported-cars.json` (fix in the wiki) and a stale `og.png`.
- The claims map: which files state each claim (44%, 12 units/frame vs 10, seven bands, 0 mph, CX-5 2022–2025 / CX-9 2021–2023).
- The alpha-longitudinal caveat (radar off, no AEB) must travel with every mention of the feature.
- Deliberate oddities not to "fix": canonical pinned to zoompilot.ai while the deploy lives on pages.dev; `repo.wiki` pointing at the pages.dev host with a flip-back comment.
- Units in prose: torque in counts, speed in mph; minimal labels in the chart plot, explanation in the figcaption.
